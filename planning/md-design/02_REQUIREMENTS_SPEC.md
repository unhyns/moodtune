# 02. Requirements Spec — MoodTune

> Scope: 기능·비기능 요구사항, 인수조건, 추적표.
> 다루지 않음: 왜 필요한지(01), 화면/컴포넌트 디자인(03), 구현 방식(04), 일정(05).

## 1. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-1 | Spotify OAuth 로그인 (Authorization Code Flow) | Must |
| FR-2 | 로그인한 사용자의 저장한 곡(Liked Songs) 및 본인이 생성한 플레이리스트 목록 조회 (팔로우한 플레이리스트는 제외) | Must |
| FR-3 | 위치 기반 현재 날씨 자동 조회 (조건 + 기온) | Must |
| FR-4 | 기분(mood) 퀵리플라이 버튼 단일 선택 | Must |
| FR-5 | 상황(situation) 퀵리플라이 버튼 단일 선택 | Must |
| FR-6 | 자연어 텍스트로 추가 맥락 입력 (옵션) | Should |
| FR-7 | 기분·날씨·상황·라이브러리를 종합한 AI 추천 요청 (Claude API) | Must |
| FR-8 | 추천 결과(곡/플레이리스트 + 추천 이유) 화면 표시 | Must |
| FR-9 | 추천 결과 클릭 시 Spotify 앱/웹으로 이동 | Must |
| FR-10 | "다시 추천받기" 재요청 액션 | Should |
| FR-11 | 날씨 자동 조회 실패 시 수동 도시 입력 대체 | Must |
| FR-12 | AI 추천 결과가 사용자 라이브러리에 실제로 존재하는 트랙인지 검증 및 폴백 처리 | Must |

### FR-12 상세 — AI 환각(hallucination) 방지
핵심 가치("항상 내 라이브러리 안에서만 추천")를 지키기 위한 필수 검증 로직.
1. Claude 응답으로 받은 트랙을 `librarySample`(요청에 포함한 라이브러리 목록)과 URI/ID 기준으로 대조한다.
2. 일치하는 트랙이 없으면, "반드시 제공된 목록 안의 트랙만 선택하라"는 제약을 프롬프트에 다시 포함해 **최대 1회** 재시도한다.
3. 재시도 후에도 라이브러리에 없는 트랙이면, `librarySample`에서 결정론적으로(예: 목록의 첫 번째 트랙) **폴백 추천**을 제공하고, 추천 이유는 일반화된 문구("지금 라이브러리에서 골라봤어요" 등)로 대체한다.
4. 이 검증/재시도/폴백 과정은 사용자에게 노출되지 않으며, 사용자는 항상 유효한 트랙 결과만 본다.

### 기분(mood) 옵션 (확정)
신남 / 차분함 / 우울함 / 집중 / 설렘

### 상황(situation) 옵션 (확정)
출근길 / 산책 / 카페 / 운동 / 드라이브

## 2. 비기능 요구사항 (Non-Functional Requirements)

| ID | 항목 | 요구사항 |
|----|------|----------|
| NFR-1 | 성능 | 입력 제출 → 추천 결과 표시까지 정상 네트워크 환경에서 수 초 이내 완료 |
| NFR-2 | 안정성/Degrade | 날씨 API 실패 시 날씨 없이 기분·상황만으로 추천 진행 (전체 흐름 차단 금지) |
| NFR-3 | 안정성/Degrade | Claude API 실패 시 재시도(retry) 액션 제공, 무한 로딩/무응답 금지 |
| NFR-4 | 개인정보 | Spotify OAuth scope는 읽기 전용 최소 권한만 요청 (쓰기/수정 권한 요청 금지) |
| NFR-5 | 데이터 최소화 | 세션에 필요한 최소 정보만 유지, 불필요한 사용자 데이터 영구 저장 금지 |
| NFR-6 | 접근성 | 03_UX_UI_SPEC.md의 접근성 규칙 준수 |

## 3. 인수조건 (Acceptance Criteria)

| FR ID | 인수조건 |
|-------|----------|
| FR-1 | 랜딩 페이지에서 Spotify 로그인 클릭 → OAuth 동의 화면 → 승인 시 토큰 발급 확인, 거부 시 에러 상태 표시 |
| FR-2 | 로그인 후 라이브러리 조회 API가 최소 1개 이상의 트랙/플레이리스트를 반환 (빈 라이브러리는 별도 안내) |
| FR-3 | 위치 권한 허용 시 입력 페이지에 날씨 조건+기온이 표시됨 |
| FR-4/5 | 기분/상황 버튼은 각각 1개만 선택 가능하며, 선택 전에는 "추천받기" 버튼 비활성화 |
| FR-6 | 자연어 입력은 비워둔 채로도 제출 가능 (필수 아님) |
| FR-7/8 | 제출 시 로딩 상태 표시 → 성공 시 최소 1개 트랙(제목/아티스트/앨범아트) + 추천 이유 문구 표시 |
| FR-9 | 추천 결과 클릭 시 새 탭/앱으로 Spotify 트랙 페이지가 열림 |
| FR-10 | "다시 추천받기" 클릭 시 동일 입력값으로 새 추천을 재요청 |
| FR-11 | 위치 권한 거부/실패 시 도시 수동 입력 필드 노출 |
| FR-12 | 라이브러리에 없는 트랙이 반환되면 1회 재시도 → 그래도 실패 시 결정론적 폴백 트랙 제공. 사용자에게는 항상 유효한(라이브러리 내) 트랙만 표시됨 |

## 6. Decisions Log
- **추천 결과 개수 (확정)**: MVP는 **항상 1곡**만 추천한다. 03/04는 이미 이 결정을 반영해 단일 카드/단일 필드로 설계되어 있었으며, 본 문서도 이에 맞춰 확정한다. 여러 곡 추천은 03/04 Open Questions에서도 다루지 않는 명확한 Out of Scope 항목으로 처리한다.
- **라이브러리 범위 (확정)**: Liked Songs + 사용자 본인이 생성한 플레이리스트만 포함한다. 팔로우한 플레이리스트는 제외한다 (01 Open Question 확정, FR-2에 반영).
- **FR-11 우선순위 조정 (확정)**: Could → Must. 날씨 자동 조회 실패 시 수동 도시 입력을 이번 MVP 범위에 포함한다.
- **FR-10 의도적 보류 (확정)**: "다시 추천받기"는 이번 MVP에서 구현하지 않는다. 이는 요구사항 누락이나 04 State 설계와의 충돌이 아니라, 다음 세션 이후 원본 입력(UserContext/WeatherContext) 전달 방식까지 포함해 별도로 재설계하기로 한 의도적 결정이다.
- **기분·상황 옵션 (확정)**: 기분 — 신남/차분함/우울함/집중/설렘, 상황 — 출근길/산책/카페/운동/드라이브.
