## Context

동기는 proposal.md의 Why, 요구사항은 `specs/guest-mode/spec.md`를 참고한다. 설계에 영향을 주는 현재 상태는 다음과 같다.

- `/input`은 마운트 시 `/api/spotify/library`를 불러 401이면 `/`로 보낸다. `/api/recommend`도 세션이 없으면 401이다. `/result`의 다시 하기 링크와 파라미터 없는 진입은 `/input`으로 간다.
- `useRecommendSubmit`이 `/api/recommend`를 고정으로 호출하고, 오류는 `failed`/`empty_library`뿐이다.
- `getRecommendation(request, now, random)`은 `librarySample`만 있으면 동작하고 안에서 다시 섞는다. `sourcesByTrackId`가 없으면 출처 문구가 붙지 않는다. Context에는 mood/situation/freeText/weather만 들어간다.
- `toPromptLabel`은 목록에 없는 칩 값을 **그대로** 프롬프트에 넣는다. 로그인 경로에서는 세션이 있어야 닿지만, 공개 경로에서는 외부 문자열이 프롬프트로 들어가는 통로가 된다.
- `lib/spotify.ts`에 `tokenRequest`가 있고 앱 토큰 함수는 없다. 앱 토큰으로 `/search`와 `/tracks/{id}`가 동작함을 2026-10-28에 실제로 확인했다.
- Spotify 개발 모드(2026년 2월 변경): `GET /tracks?ids=` 묶음 조회는 제거됐고 `GET /tracks/{id}`는 남아 있다. `/search`의 `limit` 최대값은 10이다. API 할당량은 개발자 계정 단위로 묶인다.
- OpenAI 한도: 사용자가 하루 50회로 알려 주었다. 로그인 사용자와 게스트가 같은 한도를 쓴다.
- 서버는 상태가 없는 함수 환경이라 메모리 값은 인스턴스마다 따로 있고 언제든 사라진다. DB·공유 저장소는 없다.

## Goals / Non-Goals

**Goals:**
- 로그인 경로의 코드와 동작을 바꾸지 않는다(`openai.ts`, `/api/recommend`, `/input` 불변).
- 인증 없는 공개 엔드포인트가 프롬프트 주입 통로나 비용 구멍이 되지 않게 한다.
- 후보 선택과 호출 제한을 순수 함수로 두어 시각·난수를 주입해 테스트한다.

**Non-Goals:**
- 호출 제한의 엄밀한 전역 보장. 공유 저장소 없이는 불가능하다(Decision 7).
- 곡 목록의 자동 갱신. 필요할 때 사람이 스크립트를 다시 돌린다.
- 라벨의 음악적 정확성 보장. 태그 기반이라 근사치다.

## Decisions

### Decision 1: 게스트 전용 화면과 API를 따로 둔다
- 화면은 `/guest/input`, API는 `POST /api/guest/recommend`다. 요구사항의 "게스트 /input"을 별도 경로로 구현한다.
- `/input`은 절대 좌표 레이아웃에 라이브러리 확인과 401 이동이 묶여 있어 분기를 넣으면 로그인 경로 회귀 위험이 크다. 칩 옵션(`chipColors`), `QuickReplyChip`, `WeatherBadge`, `LoadingPopup`은 재사용한다.
- 게스트 화면은 상세 디자인 전까지 세로 흐름 레이아웃으로 둔다.
- `useRecommendSubmit`의 `SubmitInput`에 `endpoint?`와 `guest?`를 더한다. 기본값은 기존과 같아 로그인 경로의 요청과 URL이 바뀌지 않는다. `guest`이면 `/result` 쿼리에 `guest=1`을 더한다.
- `/result`는 `guest=1`일 때 다시 하기 링크를 `/guest/input`으로 바꾸고 출처 문구를 보인다. 그 외 표시는 같다.

**대안**: `/input?guest=1` 분기. 경로 하나로 끝나지만 위 회귀 위험이 있고, 코드가 두 모드로 얽힌다.

### Decision 2: 곡 목록 형식과 위치
`moodtune/data/guest-catalog.json`을 저장소에 커밋하고 서버 코드에서만 import한다. `public/`에 두지 않아 데이터셋이 그대로 공개되지 않는다.
```json
{ "id": "spotifyTrackId", "name": "제목", "artist": "아티스트", "genres": ["Pop"], "countries": ["kr"] }
```
- 한 곡이 여러 국가 차트에 있을 수 있어 `countries`는 배열이다. 값은 `kr`, `us_uk`, `jp`, `world`다.
- `uri`와 `albumArtUrl`은 저장하지 않고 실행 시 만든다(uri는 ID에서, 아트는 Decision 6).
- 위 다섯 필드 외의 키가 있으면 빌드와 테스트가 실패하게 한다.

### Decision 3: 빌드 스크립트 흐름
`moodtune/scripts/build-guest-catalog.mjs`, 실행은 `node --env-file=.env.local scripts/build-guest-catalog.mjs`. 배포 빌드에 묶지 않고 사람이 돌린다. npm 의존성은 없다.
1. 8개국(`Korea, Republic of`, `United States`, `United Kingdom`, `Japan`, `France`, `Spain`, `Brazil`, `Sweden`)의 `geo.getTopTracks`로 후보를 모은다. 정확한 국가 이름은 실행 전 소량 호출로 확인한다.
2. 후보마다 `track.getTopTags`를 받아 **매핑 표**로 9개 장르에 대응시킨다(예: `hip-hop`, `rap` → Hip-Hop). 대응되는 태그가 없으면 버린다. 태그 원본은 라벨을 만든 뒤 버린다.
3. Spotify `search`(`limit` 최대 10, 앱 토큰)로 제목·아티스트를 찾고, 정규화(대소문자, 괄호·feat. 표기 제거)한 제목과 첫 아티스트가 일치할 때만 채택한다. `external_ids`나 `popularity`에 의존하지 않는다.
4. 요청 사이에 간격을 두고, 429면 `Retry-After`를 따른다. 원본 응답은 저장소 밖 임시 폴더에만 둬서 중단 후 재개에 쓰고 끝나면 지운다.
5. **빌드 게이트**: 국가별 150곡 이상을 목표로 하고, 국가 4개 × 장르 9개 표의 곡 수를 출력한다. 국가 하나라도 50곡 미만이면 파일을 쓰지 않고 실패한다. 그래서 실행 시 국가를 넓히는 경우가 생기지 않는다. 숫자는 첫 빌드 결과를 보고 사용자와 조정한다.

### Decision 4: 후보 선택은 순수 함수로 둔다
`moodtune/lib/guestCatalog.ts`의 `pickGuestCandidates(catalog, { genres, country }, random)`.
- 국가와 장르(선택 중 하나 이상)가 맞는 곡이 15곡 이상이면 그 곡들만 섞어 앞에서 최대 50곡을 쓴다.
- 15곡 미만이면 맞는 곡 전부에 같은 국가의 다른 곡을 섞어 40곡까지 채운다(국가의 곡이 그보다 적으면 있는 만큼).
- **맞는 곡이 15~39곡이면 40곡을 채우지 않고 그대로 쓴다.** 요구사항의 "40~50곡"과 "15곡 미만일 때만 넓힘"을 함께 만족할 수 없는 구간이고, 선택한 장르를 지키는 쪽을 택했다.
- 난수는 라우트 내부 인자로 주입하고(기본 `Math.random`) 본문으로 받지 않는다. 같은 난수를 `getRecommendation`에도 쓸 수 있다.

### Decision 5: `getRecommendation`을 그대로 쓴다
- `getRecommendation({ context: { mood, situation }, weather, librarySample: candidates })`로 호출한다. `openai.ts`는 바꾸지 않으므로 프롬프트 규칙과 힌트, 재시도, 폴백이 로그인 칩 경로와 같다.
- 장르·국가는 프롬프트에 넣지 않는다. 후보가 이미 걸러져 있고, Context에 넣으면 "모든 값을 reason에 쓴다" 규칙에 걸려 reason 규칙을 바꿔야 한다. 그래서 reason에는 장르가 나오지 않는다.
- 폴백은 후보 배열의 첫 곡이다. 후보 자체가 요청마다 뽑히므로 같은 요청 안에서는 결정적이지만 요청 간에는 달라진다. 항상 같은 곡이 폴백되는 것보다 낫다고 본다.
- 곡 목록 항목을 `LibraryTrack`으로 바꿀 때 `album`, `albumArtUrl`은 빈 값으로 둔다. 모델에는 uri·제목·아티스트만 간다.

### Decision 6: 앨범 아트는 고른 곡만 실행 시 조회한다
- `lib/spotify.ts`에 앱 토큰(client credentials, 만료 전까지 모듈 메모리 재사용)과 `GET /tracks/{id}`를 더한다. 추천이 정해진 뒤 한 곡만 호출한다. 묶음 조회는 개발 모드에서 제거돼 쓸 수 없다.
- 제한 시간 2초. 실패하면 `albumArtUrl: ""`로 응답한다. `/result`는 빈 값을 이미 "아트 없음" 상태로 처리한다.
- 후보 50곡 전체를 조회하지 않아 호출이 요청당 1회로 끝난다.

**대안**: 파일에 아트 URL 저장. 조회가 필요 없지만 URL이 낡을 수 있고 저장하는 Spotify 데이터가 늘어난다. 빌드 시 저장은 요구사항대로 채택하지 않는다.

### Decision 7: 호출 제한은 겹겹이 두되, 엄밀하지 않음을 받아들인다
공유 저장소가 없어 전역 한도를 정확히 셀 수 없다. 다음을 함께 쓴다. 숫자는 초기값이며 상수로 둔다.

| 층 | 방식 | 초기값 | 한계 |
|---|---|---|---|
| 브라우저 | `lib/session.ts`의 `seal`로 암호화·서명한 HttpOnly 쿠키에 날짜와 횟수 | 하루 5회 | 쿠키를 지우면 초기화 |
| 주소 | 인스턴스 메모리, `x-forwarded-for` 첫 값 기준. 주소 원문을 저장하지 않고 해시 | 분당 3회 | 인스턴스마다 따로 |
| 게스트 전체 | 인스턴스 메모리의 날짜별 AI 호출 수 | 하루 20회 | 인스턴스 수만큼 늘고, 재시작하면 초기화 |
| 최종 방어 | OpenAI 대시보드의 사용 한도 | 사용자가 설정 | 로그인 사용자도 함께 막힘 |

- 순서: 요청 검증(400은 세지 않음) → 제한 확인(429, AI 호출 없음) → 카운트 → 추천. 재시도도 AI 호출이지만 게스트 전체 수는 요청 단위로 세어 단순하게 둔다.
- 하루 경계는 Asia/Seoul이다. 판정 함수는 `moodtune/lib/guestLimit.ts`의 순수 함수로 두고 시각을 주입한다.
- `useRecommendSubmit`에 `guest_limit` 오류를 더한다. 화면 문구: "오늘 체험 횟수를 다 썼어요. 내일 다시 와주세요."
- 하루 50회 중 게스트에 20회를 배정한 것은 로그인 사용자 몫을 남기기 위해서다.

**대안**: 공유 저장소(Vercel Marketplace의 Redis 등)로 전역 카운터. 가장 정확하지만 새 외부 서비스라 프로젝트 규칙상 별도 승인이 필요하다. 트래픽이 늘면 다시 검토한다. Vercel Firewall 규칙은 코드 없이 주소 제한을 더할 수 있어 배포 후 보강책으로 둔다.

### Decision 8: 공개 엔드포인트의 입력은 허용 목록으로만 받는다
- mood·situation은 `chipColors`의 라벨, genres·country는 정해진 값만 받는다. 목록 밖이면 400이라 `toPromptLabel`의 통과 경로에 닿지 않는다.
- weather는 `temperatureC`가 유한한 숫자이고 `icon`이 짧은 영숫자일 때만 쓰고, 문자열 필드 길이를 제한한다. 프롬프트에는 `weatherDayPhrase` 결과만 들어가므로 `condition`은 전달하지 않는다.
- `readSession`을 호출하지 않는다. 로그에 선택값을 남기지 않는다.

### Decision 9: 출처 표시
`/guest/input`과 `guest=1`인 `/result`에 "곡 선정 참고: Last.fm"을 https://www.last.fm 링크로 둔다. 로그인 화면에는 넣지 않는다. 약관이 요구하는 표기 형식은 tasks 0.1에서 확인한다.

## Risks / Trade-offs

약관 내용은 2026-11-02에 공개 페이지를 요약 도구로 읽은 것이다. 원문 확인이 필요하고 법률 판단이 아니다.

- [Last.fm: 비상업 용도 한정] API 약관은 데이터를 비상업 목적으로만 허용하고 상업적 이용에는 별도 계약을 요구한다. 수업 프로젝트로는 해당하지 않을 수 있지만 유료화·광고를 붙이면 달라진다. → 사용자가 용도를 확인한다(tasks 0.1).
- [Last.fm: 저장·삭제·표기] 저장은 적은 양으로 제한되고(사용 상한 100MB), 약관 종료 시 데이터 삭제와 출처 표기, 링크 규칙이 있다. 순위·태그를 저장하지 않아도 **라벨이 Last.fm 데이터에서 나온 파생물로 보일 수 있다.** → 표기를 지키고, 접근이 끊기면 파일을 지울 수 있도록 빌드를 재현 가능하게 둔다.
- [Spotify: 메타데이터의 AI 입력] 개발자 정책에 "Spotify 콘텐츠를 머신러닝·AI 모델에 넣지 말라"는 취지의 조항이 있다. **이 조항은 게스트만의 문제가 아니다.** 이미 로그인 경로도 곡 제목과 아티스트를 OpenAI에 보낸다. 게스트 목록의 제목·아티스트를 어느 쪽 데이터로 볼지도 불분명하다. → tasks 0.1에서 사용자가 판단하고, 필요하면 별도 change로 다룬다.
- [Spotify: 다른 서비스와의 결합, 메타데이터 단독 제공] 다른 서비스의 콘텐츠와 통합한 제품, 메타데이터를 단독 제공하는 제품을 제한하는 조항이 있다. Last.fm으로 고르고 Spotify로 검증하는 구조가 해당하는지 확인이 필요하다. → 앱은 실행 중 Last.fm을 호출하지 않고 파일을 공개하지 않지만, 해소됐다고 볼 수는 없다.
- [개발 모드 앱 토큰] 마이그레이션 가이드는 앱 토큰 요청의 허용 여부를 명시하지 않는다. 2026-10-28에는 동작했다. 할당량이 계정 단위라 게스트의 트랙 조회가 로그인 사용자와 몫을 나눈다. → 조회는 요청당 1회로 제한하고, 실패해도 추천은 표시한다.
- [호출 제한 우회] 쿠키 삭제, 주소 변경, 인스턴스 증가로 넘을 수 있다. → 최종 방어는 OpenAI 대시보드 한도이며, 그때는 로그인 사용자도 막힌다.
- [차트 편향] Last.fm 사용자 구성상 한국·일본 차트가 실제 인기와 다르거나 Ballad·K-POP 곡이 적을 수 있다. 태그가 없어 버려지는 곡도 많을 수 있다. → 빌드 게이트 표로 확인하고, 15곡 확장이 자주 일어나는 조합을 보고한다.
- [곡 목록 노후화·삭제] 트랙이 지역 제한되거나 사라질 수 있다. 재생 링크가 열리지 않을 수 있다. → 사람이 다시 빌드한다. 아트 조회 실패 시에도 추천은 표시한다.
- [UI 임시 디자인] Figma 전까지 세로 흐름 레이아웃이다. → 상세 디자인은 후속 작업이다.

## Migration Plan

- 저장소 데이터·기존 API 변경이 없다. `LASTFM_API_KEY`는 빌드를 돌리는 환경의 `.env.local`에만 두고 배포 환경에는 넣지 않는다.
- 배포 전에 OpenAI 대시보드 사용 한도를 설정한다.
- 되돌리기: 랜딩 링크를 빼면 진입이 막힌다. 새 경로와 파일은 독립적이라 지워도 로그인 경로에 영향이 없다.
