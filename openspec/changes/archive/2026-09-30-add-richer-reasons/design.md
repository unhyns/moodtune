## Context

현재 구조 (`moodtune/`):
- `lib/spotify.ts` `fetchLibrary()`는 좋아요 곡(최대 200곡, 최근순)을 먼저 담고, 본인이 만든 플레이리스트(최대 10개 × 100곡)의 곡 중 **아직 없는 곡만** 뒤에 붙인다. 이때 플레이리스트 이름은 `playlists[]` 요약에만 남고 곡과의 연결은 버려진다. 좋아요 곡이 플레이리스트에도 있으면 중복 제거되면서 출처 정보가 사라진다.
- `app/api/recommend/route.ts`는 `library.tracks.slice(0, 50)`을 `librarySample`로 `getRecommendation()`에 넘긴다. 좋아요가 50곡 이상인 사용자는 샘플이 전부 좋아요 곡이다.
- `lib/openai.ts`는 `{uri, name, artist}` 목록과 `mood/situation/note/weather` 줄을 프롬프트에 넣고, 이유를 "one short, friendly sentence in Korean"으로 요청한다. 반환된 `track`은 `librarySample`의 객체 그대로다.
- `LibraryTrack` 객체는 `/api/spotify/library` 응답(`tracks[]`)과 `/api/recommend` 응답(`track`)에 그대로 직렬화된다. 이 두 응답의 형태는 이번 change에서 바꾸지 않는다.

## Goals / Non-Goals

**Goals:**
- 곡별 출처 플레이리스트 이름을 서버 내부에서 유지하고, 좋아요 곡이 본인 플레이리스트에도 있으면 그 출처까지 붙인다.
- 프롬프트 규칙을 강화해 입력값 언급, 사실 주장 제한, 출처 근거 사용, 한국어 1~2문장을 요구한다.
- 두 API 응답의 형태가 바뀌지 않음을 구조적으로 보장한다.

**Non-Goals:**
- 샘플링 전략(50곡, 좋아요 우선) 변경 — `add-album-playlist-recommendation`에서 다룬다.
- 이유 문구의 사후 검증 및 검증 실패 시 재시도 — 재시도·폴백 로직은 이번 범위에서 제외했다.
- UI, 폴백 문구, 모델·temperature 변경.

## Decisions

### 1. 출처 정보는 `LibraryTrack`에 넣지 않고 별도 맵으로 전달
`LibraryTrack`에 `sourcePlaylists?` 필드를 추가하면 두 응답에 그대로 직렬화되어 응답 스키마가 바뀐다. 매번 필드를 제거하는 방식은 누락되기 쉽다. 대신 `fetchLibrary()`가 `LibraryResponse`와 함께 **`sourcesByTrackId: Record<string, string[]>`**(트랙 ID → 본인 플레이리스트 이름 목록)를 반환하도록 한다.
- `/api/spotify/library`는 기존처럼 `LibraryResponse` 부분만 응답한다.
- `/api/recommend`는 맵 전체가 아니라 **추천 후보(`librarySample`, 최대 50곡)의 트랙 ID에 해당하는 항목만** 골라 `RecommendationRequest.sourcesByTrackId?`(서버 내부 타입)로 넘긴다. 선택될 수 있는 곡은 후보뿐이라 후보 밖 곡의 출처는 쓰일 일이 없으므로 넘기지 않는다.
- `getRecommendation()`이 돌려주는 `track`은 여전히 `librarySample`의 순수 `LibraryTrack`이므로 추천 응답 형태도 그대로다.

`Map` 대신 `Record`를 쓰는 이유는 기존 코드가 일반 객체와 JSON 위주로 작성되어 있기 때문이다. 이 맵은 직렬화되어 응답에 나가지 않는다.

**기각한 대안**: `fetchLibrary()`의 반환 타입은 그대로 두고 출처만 따로 조회하는 함수를 추가하는 방식. 플레이리스트 곡 목록을 다시 요청해야 하므로 Spotify 호출이 두 배가 되어 기각했다.

### 2. 좋아요 곡에도 출처를 붙임
플레이리스트를 순회할 때 중복 여부와 관계없이 모든 곡의 트랙 ID에 해당 플레이리스트 이름을 추가한다. 중복 제거(`seen`)는 `tracks` 배열에만 적용한다. 좋아요가 50곡 이상인 사용자는 샘플이 모두 좋아요 곡이므로, 이렇게 해야 출처 근거가 실제로 쓰일 수 있다.
- 플레이리스트 순서는 `/me/playlists` 응답 순서를 따르고, 같은 플레이리스트 이름이 한 곡에 중복으로 붙지 않게 한다.
- 조회에 실패한 플레이리스트는 지금처럼 건너뛰고 출처도 남기지 않는다.
- 팔로우한 플레이리스트는 이미 `owner.id === me.id` 필터로 제외되어 있어 출처 후보가 되지 않는다.

### 3. 출처 플레이리스트는 모델에 넘기지 않고, 인용 문장은 코드가 붙인다
이유는 두 부분으로 만든다.
- **모델이 만드는 부분**: 입력값(기분/상황/날씨)만으로 된 한국어 **정확히 1문장**. 트랙 목록 JSON은 `{uri, name, artist}`만 담고 `playlists`는 넣지 않는다. 프롬프트에는 플레이리스트에 대한 지시가 없고, "플레이리스트는 절대 언급하지 않는다"는 조건 없는 규칙 하나만 둔다.
- **코드가 붙이는 부분**: `getRecommendation()`이 곡을 확정하고 `isFallback: false`일 때만, 선택된 곡이 `sourcesByTrackId`에 출처를 가지면 모델 문장 뒤에 `'{이름}' 플레이리스트에 넣어두신 곡이에요.`를 결정적으로 붙인다. 출처가 없으면 모델 문장 1개를 그대로 둔다.
  - 이름은 출처 목록(`/me/playlists` 순서)의 **첫 번째**만 쓴다. 40자를 넘으면 단어 중간이 아니라 40자 안의 마지막 공백에서 자르고 말줄임표(`…`)를 붙인다. 40자 안에 공백이 없으면 40자에서 자르고 `…`를 붙인다. 7차 샘플에서 40자 고정 자르기가 "만든 테"처럼 단어 중간에서 끊겨 바꿨다.
  - 모델 문장이 마침표·물음표·느낌표 등으로 끝나지 않으면 마침표를 붙인 뒤 잇는다.
  - 재시도로 얻은 곡에도 같은 방식으로 붙인다. 폴백(`isFallback: true`)에는 붙이지 않는다(Decision 5).

따라서 이유는 출처가 없으면 1문장, 있으면 2문장이다. 스펙의 "1~2문장" 범위 안이다.

- **범위**: `/api/recommend`가 후보(최대 50곡)에 해당하는 출처만 넘기고(Decision 1), 인용 대상은 선택된 곡 하나뿐이다.
- **데이터로만 취급**: 플레이리스트 이름은 사용자가 입력한 임의의 문자열이지만, 이제 모델 프롬프트에 들어가지 않아 지시문처럼 해석될 경로가 없다. 코드가 그대로 끼워 넣어 같은 사용자에게만 보여준다.

### 4. 이유의 근거 우선순위와 규칙
이유 문장의 근거와 우선순위는 다음과 같다.
1. **입력값**(mood / situation / weather 중 주어진 것) — 모델이 만드는 1문장의 유일한 근거. 항상 하나 이상 언급한다.
2. **출처 플레이리스트**(선택된 곡에 출처가 있을 때) — 있으면 **항상** 인용한다. 모델이 아니라 코드가 붙인다(Decision 3).
3. **곡 자체 설명**(소리·장르·템포·가사·인상) — **금지**. 곡 제목과 아티스트 이름을 부르는 것만 허용한다.

모델이 곡을 모르는 경우가 많고 틀려도 사용자가 알아채기 어려운 반면, 입력값과 출처는 사용자가 직접 확인할 수 있기 때문이다.

시스템 프롬프트의 `reason` 규칙:
- 한국어 정확히 1문장. 두 번째 문장을 붙이지 않는다.
- 입력값으로만 구성하고, 플레이리스트는 절대 언급하지 않는다.
- Context에 주어진 값을 **모두** 쓴다. 기분과 상황이 둘 다 있으면 하나를 버리지 않고 한 문장 안에 엮는다. 각 표현의 의미와 핵심 단어는 유지하고, 둘을 잇기 위한 어미 조정만 허용한다. 다른 기분·상황으로 바꾸지 않는다.
- 날씨 줄이 있으면 지금 상황을 설명하는 용도로 자연스럽게 넣는다. 조건은 받은 그대로 쓰고, 기온은 숫자로만 쓸 수 있다. 받은 값에 없는 체감 표현(예: 27°C인데 "선선한")을 덧붙이지 않고, 날씨를 곡과 연결하지 않는다. 날씨 줄이 없으면 날씨를 언급하지 않는다.
- 주어지지 않은 값은 언급하지 않는다.
- 곡의 소리·장르·템포·가사·분위기·인상 등 곡 자체에 대한 말은 절대 하지 않는다. 곡을 입력과 잇는 표현("~에 어울린다", "~하기 좋다", "~한 분위기와 맞다" 등)도 금지한다.
- 예시의 입력값은 `MOOD_OPTIONS`/`SITUATION_OPTIONS` 라벨과 겹치지 않는 가상의 표현("나른한 기분", "도서관에 가는 중", "흐림, 15°C")으로 쓰고, 예시 문장을 베끼지 말라고 명시한다. 기분·상황·날씨를 모두 엮은 좋은 예와, 같은 입력에서 상황·날씨를 빠뜨린 나쁜 예를 둔다.

기분·상황 값은 클라이언트에서 영문 칩 라벨(Calm, 🚙 Driving 등)로 오지만, 프롬프트에는 `lib/chipColors.ts`의 `MOOD_OPTIONS`/`SITUATION_OPTIONS`에 둔 한국어 표현(`promptLabel`, 예: 차분한 기분, 운전하는 중)으로 바꿔 넘긴다. API 요청 값과 UI 표시는 그대로다.

**1~6차 샘플 검증 요약 (tasks 4.2)**
- 1차: 곡 설명을 "제목과 아티스트만으로 확실한 것"으로 허용하고, 좋은 예시에 `'출근길' 플레이리스트` 문장을 두었다. 출처 인용은 6/6이었지만, 출처 없는 곡에도 플레이리스트 이름을 지어냈다(1건).
- 2차: 예시를 입력값만 쓰는 문장으로 바꾸고 주관적 인상 평가를 금지했다. 지어내기는 0/4가 됐지만 출처 인용도 0/6이 됐고, 곡과 입력을 잇는 문장 때문에 (c) 위반이 5/10으로 늘었다.
- 3차: 곡 설명을 장르·템포·아티스트 스타일로 한정하고 연결 표현을 금지했다(절충안). 8/10으로 미달이었고, 출처 인용은 0/6이었다.
- 4차: 곡 자체 설명을 완전히 금지하고, 출처 인용을 필수 규칙으로 바꿨다. 출처 인용은 6/6이 됐지만, 두 번째 문장에서 연결 표현 위반 3건과 받지 않은 기분 언급 2건이 나왔다.
- 5차: 1문장으로 제한하고 기분·상황을 한국어 라벨로 넘겼다. 곡 설명 위반은 0건이 됐지만, 실제 라벨로 된 예시 문장을 베낀 사례와 출처 없는 곡의 제목을 플레이리스트처럼 쓴 사례가 1건씩 나왔다.
- 6차: 예시를 가상 표현으로 바꾸고 나쁜 예를 추가했다. 예시를 베끼는 문제는 사라졌지만, 출처 없는 곡에 플레이리스트를 지어낸 경우가 2/4로 늘었다(없는 이름 1건, 곡 제목 1건).

- 7차: 인용을 코드로 옮겼다(아래). (a)~(f)는 10/10이었지만, 모든 이유가 "{입력 하나}이라 이 곡을 골랐어요."로 수렴했다. 기분과 상황이 둘 다 있어도 하나만 쓰고, 날씨가 있어도 한 번도 언급하지 않았다.
- 8차(최종): 받은 입력값을 모두 쓰도록 했다(아래 "8차 조정 이유"). 샘플은 기분+상황과 날씨가 있는 조합 위주로 뽑았다.

**최종 판정 (2026-09-30)**: 8차에서 샘플 검증(tasks 4.2)을 마무리한다. (a)~(f)는 10/10 통과했다. 입력값 반영은 9/10이다. 남은 1건은 "집중하는 중 + 카페에 있는 중"처럼 두 표현이 모두 "~하는 중"이라 한 문장에 자연스럽게 엮이지 않는 특수 케이스로 보고, 추가 조정 없이 완료로 판정했다. 모든 이유가 비슷한 문장 틀로 모이는 단조로움은 규칙 위반이 아니므로 이번 change에서 다루지 않는다.

**8차 조정 이유**: 1~7차는 불확실한 대상을 다뤘다. 모델이 제목과 아티스트만으로 알 수 없는 곡의 성격, 곡마다 있는지 없는지 판단해야 하는 플레이리스트가 그것이었고, 그래서 모델이 모르는 것을 지어내거나 조건을 잘못 판단하는 실패가 반복됐다. 8차는 서버가 이미 확정해 넘기는 입력값(기분·상황·날씨)을 빠짐없이 쓰게 하는 것뿐이다. 모델이 새로 알아내거나 판단할 대상이 없으므로 같은 종류의 실패 위험이 없다. 곡에 대해서는 여전히 아무것도 추가하지 않는다. 남는 위험은 날씨를 체감 표현으로 바꾸면서 받은 값과 다른 말을 하는 것인데, 조건은 받은 그대로 쓰고 기온은 숫자로만 쓰게 해서 막는다.

**인용을 프롬프트에서 코드로 옮긴 이유**: "출처가 있을 때만 인용하고, 없으면 언급하지 않는다"는 조건부 판단을 모델이 반복해서 실패했다. 허용 규칙(2~3차)이면 출처가 있어도 인용하지 않았고(0/6), 필수 규칙(1·4~6차)이면 출처가 없는 곡에도 이름을 지어냈다(1/4, 1/4, 2/4). 규칙 문구, 좋은 예·나쁜 예, 예시 교체를 거치는 동안 한쪽을 고치면 다른 쪽이 나빠졌다. 출처 유무는 서버가 이미 정확히 아는 값이므로, 모델에게 판단을 맡기지 않고 코드가 결정적으로 붙이는 편이 인용 누락과 지어내기를 모두 구조적으로 없앤다. 모델에게는 "플레이리스트는 절대 언급하지 않는다"는 조건 없는 규칙만 남긴다.

**기각한 대안**: 응답 후 입력값 언급 여부와 문장 수를 코드로 검사해 재요청하는 방식. 재시도 로직 변경이 범위 밖이고, 한국어로 풀어 쓴 표현을 입력 라벨과 기계적으로 대조하기 어려워 기각했다. 대신 수동 샘플 검증으로 확인한다(tasks 참고). 출처 인용 문장을 붙이는 것은 검사나 재요청이 아니라 이미 아는 사실의 결정적 조립이라 이 기각과 충돌하지 않는다.

### 5. 폴백·재시도 경로는 그대로
`GENERIC_FALLBACK_REASON`, 1회 재시도, `librarySample[0]` 폴백은 건드리지 않는다. 재시도 호출(`forceListOnly: true`)도 같은 프롬프트 규칙을 받고, 재시도로 얻은 곡에도 출처 인용 문장을 붙인다. 폴백(`isFallback: true`)에는 인용 문장을 붙이지 않고 기존 일반화된 이유를 그대로 쓴다. 폴백 이유는 `ai-recommendation` 델타의 `Unchanged Response Shape and Fallback Behavior` 요구사항에서 예외로 명시했다.

## Risks / Trade-offs

- [프롬프트 지시만으로는 규칙 준수를 보장할 수 없음] → gpt-4o-mini가 가끔 입력을 빠뜨리거나 곡 분위기를 단정할 수 있다. **Mitigation**: 규칙을 짧고 구체적으로 쓰고 가상 표현으로 된 좋은 예·나쁜 예를 넣는다. 모델이 반복해서 실패한 조건부 판단(출처 인용)은 코드로 옮겼다(Decision 3). 수동 샘플 검증에서 위반이 잦으면 후속 change에서 사후 검증을 검토한다.
- [플레이리스트 이름은 사용자가 입력한 문자열] → 모델 프롬프트에 넣지 않으므로 이름 속 지시문이 모델에 영향을 줄 수 없다. 코드가 40자로 잘라 인용 문장에 그대로 넣고, 그 이름을 만든 사용자 본인에게만 보인다.
- [40자에서 잘린 이름이 어색할 수 있음] → 공백 기준으로 자르고 `…`를 붙여 단어 중간에서 끊기지 않게 한다. 공백 없이 40자를 넘는 이름만 40자에서 끊긴다.
- [좋아요 곡이 많은 사용자는 플레이리스트 전용 곡이 샘플에 들어가지 않음] → 출처 근거는 "좋아요 + 플레이리스트에 모두 있는 곡"에서 주로 쓰인다. 샘플링 개선은 이후 change에서 다룬다.
- [출처가 여럿이어도 첫 번째 이름만 인용] → `/me/playlists` 순서상 첫 번째가 가장 관련 있는 이름이라는 보장은 없다. 문장을 짧고 결정적으로 유지하는 쪽을 택했다.
