# Planning Review

`planning/md-design/`의 설계 문서가 지금 상태로 구현을 시작해도 되는지 점검하는 리뷰 전용 Skill입니다. 문서를 읽고 리포트만 출력하며, 어떤 파일도 수정하지 않습니다.

## 언제 사용하는가
- 사용자가 명시적으로 설계 문서 검토/구현 준비 상태 확인을 요청했을 때만 실행한다.
- 문서가 수정되었다고 해서, 혹은 다른 작업 맥락에서 자동으로 제안하거나 실행하지 않는다.
- 코드 구현 작업의 일부로 스스로 판단해 끼워 넣지 않는다.

## 실행 절차

1. `planning/md-design/01_PRODUCT_BRIEF.md` → `02_REQUIREMENTS_SPEC.md` → `03_UX_UI_SPEC.md` → `04_TECHNICAL_DESIGN.md` → `05_DELIVERY_PLAN.md` 순서로 5개 파일을 전부 읽는다. 이 5개 외의 문서(`docs/`, `CLAUDE.md` 등)는 검토 범위에 포함하지 않는다.
2. 아래 "검토 기준" 4가지 각각에 대해 5개 문서를 교차 확인하며 근거를 수집한다. 근거 없이 판단하지 않는다 — 확실하지 않으면 ⚠️로 표시하고 이유를 남긴다.
3. "출력 형식"에 맞춰 체크리스트를 작성한다.
4. 문서를 수정하지 않는다. 사용자가 이어서 "반영해줘"라고 요청하면 그때 별도로 수정한다.

## 검토 기준

### 1. 문서 간 충돌
같은 사안에 대해 두 문서 이상이 서로 다른 내용을 말하는 경우를 찾는다.
- 예: 한 문서는 이미 결정된 것처럼 서술하는데 다른 문서는 아직 미정(Open Question)이라고 되어 있는 경우
- 예: 화면/데이터 모델/요구사항이 서로 다른 개수·구조를 전제하는 경우
- 예: 같은 기능의 흐름 순서(언제 무엇을 하는지)가 문서마다 다르게 암시되는 경우

### 2. 빠진 요구사항
5개 문서 전체를 봐도 어디에도 정의되어 있지 않은, 하지만 핵심 플로우상 반드시 필요한 항목을 찾는다.
- 예: 핵심 가치와 직결된 검증/안전장치가 요구사항으로 존재하지 않는 경우
- 예: 정상 케이스만 있고 실패/예외/빈 데이터 케이스가 빠진 경우
- 예: 화면 간 전환·상태 전달처럼 없으면 동작이 막히는 흐름이 어디에도 명시되지 않은 경우

### 3. MVP 범위 초과
지금 범위대로면 정해진 일정 안에 완성하기 벅찬 부분을 찾는다.
- 예: 우선순위(Must/Should/Could) 태그가 특정 등급에 과도하게 몰려 있어 실질적으로 기능을 못 거르는 경우
- 예: 데모/MVP 목적에 비해 과도하게 정교한 인프라(보안, 인증, 캐싱 등)를 요구하는 경우
- 예: 낮은 우선순위(Should/Could)로 표시된 기능이 정작 화면·데이터 설계에는 필수처럼 이미 박혀 있어 실제로는 뺄 수 없는 경우

### 4. 애매한 결정
구현자가 문서만 보고는 스스로 임의로 골라야 하는 지점을 찾는다.
- 예: "예를 들어", "~로 가정", "TODO: 확정 필요"처럼 옵션만 나열하고 하나로 확정하지 않은 서술
- 예: 여러 구현 방법이 가능한데 그중 하나를 특정하지 않은 기술적 결정
- 예: 뒤 문서가 앞 문서의 미정 사항을 이미 특정 값으로 전제하고 있어, 정작 결정이 어디서 내려졌는지 불명확한 경우

## 출력 형식

각 기준마다 발견 항목을 체크리스트로 나열한다. 상태 기호는 다음 기준으로 붙인다.
- ✅ 문제 없음 (근거: 어떤 부분을 확인했는지 한 줄로)
- ⚠️ 경미한 이슈 — 구현을 막지는 않지만 확정해두는 것을 권장
- ❌ 구현 착수 전 반드시 해결해야 함 — 그대로 구현하면 재작업이 발생하는 지점

```
## Planning Review 결과

### 1. 문서 간 충돌
- [✅/⚠️/❌] <내용> — <근거: 문서명/항목>

### 2. 빠진 요구사항
- [✅/⚠️/❌] <내용> — <근거>

### 3. MVP 범위 초과
- [✅/⚠️/❌] <내용> — <근거>

### 4. 애매한 결정
- [✅/⚠️/❌] <내용> — <근거>

### 종합 판단
- ❌ 개수: N개 / ⚠️ 개수: N개
- 구현 착수 가능 여부: [지금 착수 가능 / ❌ 항목만 먼저 해결 후 착수 / 전면 재검토 필요]
```

각 카테고리에 해당 사항이 없으면 "해당 없음 — 발견된 이슈 없음" 한 줄만 남기고 억지로 항목을 만들지 않는다.

## 하지 말아야 할 행동
- `planning/md-design/` 파일이든 다른 어떤 파일이든 수정하지 않는다. 리포트만 출력한다.
- 사용자의 명시적 요청 없이 스스로 판단해 실행하지 않는다.
- 근거가 불충분한데 ✅로 단정하지 않는다 — 확실하지 않으면 ⚠️로 표시하고 왜 확실하지 않은지 적는다.
- `planning/md-design` 5개 파일 외의 문서(`docs/`, `CLAUDE.md`, 소스 코드 등)를 검토 기준에 끌어와 범위를 넓히지 않는다.
- 리뷰 도중 발견한 문제에 대해 코드나 문서 수정안을 먼저 작성해서 제시하지 않는다 — 판단과 근거까지만 제공하고, 수정은 사용자가 별도로 요청할 때 진행한다.
- 이전 대화나 기억에 의존해 판단하지 않는다 — 실행 시점의 실제 파일 내용을 다시 읽어서 검토한다.
